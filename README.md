# Lolka_Bot

Telegram-бот для сбора пользовательских ответов по динамическим формам и отправки итогового отчёта в канал Lolka.

## Требования

### Runtime
- Python 3.11+
- `pip`/`venv` для установки зависимостей
- Доступ к Telegram Bot API

### База данных
- PostgreSQL 14+
- Выделенная БД и пользователь с правами на чтение/запись

## Переменные окружения

Ниже приведён базовый набор переменных окружения (через `.env` или экспорт в shell):

- `BOT_TOKEN` — токен Telegram-бота от BotFather
- `DATABASE_URL` — строка подключения к PostgreSQL, например:
  - `postgresql+asyncpg://lolka_user:lolka_pass@localhost:5432/lolka_bot`
- `LOLKA_CHANNEL_ID` — ID/username канала для отправки отчётов (например, `@lolka_reports` или `-100xxxxxxxxxx`)
- `API_BASE_URL` — базовый URL backend API форм
- `API_TIMEOUT_SECONDS` — таймаут запросов к API (рекомендуется 10–30)
- `MAX_RETRIES` — количество повторных попыток при временных ошибках
- `LOG_LEVEL` — уровень логирования (`INFO`, `WARNING`, `ERROR`, `DEBUG`)

> Если в проекте используются дополнительные переменные (например, для webhook/redis), добавьте их в этот раздел в том же формате.

## Поток данных

1. **Создание формы**
   - Администратор/сервис формирует форму в backend API: название, поля, обязательность, типы значений.
   - Форма получает `form_id` и сохраняется в БД.

2. **Отображение пользователю**
   - Бот получает событие (или команду), что форма доступна пользователю.
   - Бот последовательно отправляет вопросы пользователю в Telegram.
   - Ответы валидируются на каждом шаге (тип, обязательность, ограничения).

3. **Отправка отчёта в канал**
   - После заполнения всех полей бот формирует итоговый отчёт.
   - Отчёт отправляется в канал Lolka в виде структурированного сообщения.
   - В БД сохраняются статус отправки и метаданные (`message_id`, время, пользователь).

Схема:

`Backend/API -> Bot -> User answers -> Bot report builder -> Lolka channel`

## Пример: создание формы и заполнение пользователем

### Пример формы (JSON)
```json
{
  "form_id": "daily_shift_001",
  "title": "Ежедневный отчёт смены",
  "fields": [
    {"id": "shift_date", "label": "Дата смены", "type": "date", "required": true},
    {"id": "operator_name", "label": "Имя оператора", "type": "string", "required": true},
    {"id": "tickets_done", "label": "Закрыто тикетов", "type": "integer", "required": true},
    {"id": "notes", "label": "Комментарий", "type": "string", "required": false}
  ]
}
```

### Пример диалога с пользователем
- Бот: `Дата смены (YYYY-MM-DD)?`
- Пользователь: `2026-05-19`
- Бот: `Имя оператора?`
- Пользователь: `Ирина`
- Бот: `Закрыто тикетов?`
- Пользователь: `17`
- Бот: `Комментарий (можно пропустить)?`
- Пользователь: `Сложный кейс по эскалации`
- Бот: `Спасибо! Отчёт отправлен в канал.`

## Ошибки и восстановление

### 1) Retry-логика
- Для временных ошибок сети/таймаута используйте экспоненциальный backoff (например, 1s, 2s, 4s).
- Ограничивайте число попыток через `MAX_RETRIES`.
- Логируйте каждую попытку с причиной ошибки.

### 2) Недоступность API
- Если API форм недоступно:
  - вернуть пользователю понятное сообщение: «Сервис временно недоступен, попробуйте позже»;
  - сохранить черновик ответов (если есть) в БД;
  - поставить задачу на повторную отправку отчёта в фоновой очереди.

### 3) Невалидные ответы пользователя
- На каждом поле делать проверку типа и бизнес-правил.
- При ошибке не прерывать процесс: показать пример корректного формата и повторить вопрос.
- После N неудачных попыток:
  - предложить пропустить необязательное поле;
  - либо завершить форму со статусом `validation_failed`.

### 4) Сбои при отправке в канал
- Если Telegram API вернул ошибку отправки:
  - сохранить отчёт в очередь повторной доставки;
  - пометить запись статусом `delivery_pending`;
  - при успешной повторной отправке обновить статус на `delivered`.

### 5) Наблюдаемость
- Обязательные метрики: количество созданных форм, успешно завершённых форм, ошибок валидации, ошибок доставки.
- Настроить alerting на рост 5xx ошибок API и на увеличение очереди `delivery_pending`.
